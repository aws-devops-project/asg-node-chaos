# ASG Node Chaos

A small Node.js lab app for testing an AWS Application Load Balancer (ALB), Auto Scaling Group (ASG), target-group health checks, and CloudWatch alarms. It includes a live dashboard, host resource graphs, chaos controls, and a bounded load generator that can send traffic to an ALB.

> **Lab use only:** Chaos controls and the load-test API do not require authentication. Keep this app private, restrict access with security groups/firewalls, and only send test traffic to infrastructure you own. Load and scale-out can incur AWS charges.

## Requirements

- Node.js 18 or later (Node.js 20+ recommended).
- npm.
- For AWS testing: an EC2 instance in an ALB target group. The app itself does not create AWS resources or configure CloudWatch alarms.

## Install and start locally

From the project directory, install the dependencies:

```powershell
npm install
```

Run the app on localhost (no PM2 required):

```powershell
$env:HOST = '127.0.0.1'
$env:PORT = '3000'
npm start
```

Open <http://localhost:3000>. Keep the terminal running; press **Ctrl+C** to stop the server. `HOST` and `PORT` are optional. By default, the app listens on `0.0.0.0:80`, which is suitable for an EC2 target but may require elevated permissions locally.

## Dashboard sections

- **Instance & ALB info:** shows the request host, client address, and instance ID, Availability Zone, and private IP when running on EC2 with IMDSv2 available. Outside EC2, local fallback values are displayed.
- **Live traffic:** request count, average response time, HTTP 5xx count, and a rolling traffic graph.
- **Host utilization:** CPU, RAM, and root-volume usage graphs, sampled once per second for the local app host.
- **Recent request logs:** latest 50 requests handled by this process.
- **Chaos controls:** configurable HTTP 500 rate, timed CPU and RAM spikes, and a target health toggle.
- **ALB load test:** sends bounded GET requests from the app host to an AWS ALB URL.

Metrics and chaos state are in memory, scoped to a single app process/instance, and reset on restart. Behind an ALB, dashboard metrics are **per target**, not aggregated across the ASG. Host resource graphs report the host, not container-specific resource usage.

## Test the chaos controls

Use the dashboard controls, or call the APIs directly. In PowerShell, examples follow.

Set injected HTTP 500s to 20%:

```powershell
$body = @{ errorRate = 20 } | ConvertTo-Json
Invoke-RestMethod -Uri 'http://localhost:3000/api/chaos/config' `
	-Method Post -ContentType 'application/json' -Body $body
```

Reset the error rate and verify the ALB health-check endpoint:

```powershell
$body = @{ errorRate = 0; isHealthy = $true } | ConvertTo-Json
Invoke-RestMethod -Uri 'http://localhost:3000/api/chaos/config' `
	-Method Post -ContentType 'application/json' -Body $body
Invoke-WebRequest -UseBasicParsing 'http://localhost:3000/health'
```

Trigger a short CPU spike (duration is 1–300 seconds):

```powershell
$body = @{ durationSeconds = 10 } | ConvertTo-Json
Invoke-RestMethod -Uri 'http://localhost:3000/api/chaos/cpu' `
	-Method Post -ContentType 'application/json' -Body $body
```

Trigger a short RAM spike (16–512 MB, duration 1–300 seconds). The app enforces an available-memory safety reserve, so a request can be rejected if the host is low on memory:

```powershell
$body = @{ memoryMb = 64; durationSeconds = 10 } | ConvertTo-Json
Invoke-RestMethod -Uri 'http://localhost:3000/api/chaos/memory' `
	-Method Post -ContentType 'application/json' -Body $body
```

Use **Target Group Health** in the dashboard to make `/health` return 503, observe the target become unhealthy, then toggle it back to healthy. Configure the target group's health-check path as `/health`. If testing ASG replacement, make sure the ASG health-check type includes ELB and understand that an unhealthy target can be terminated and replaced.

## Run a bounded test against your ALB

In the dashboard's **ALB load test** section:

1. Enter your ALB DNS URL, for example `http://my-alb-123.us-east-1.elb.amazonaws.com/`.
2. Start conservatively, such as **1 request/second for 10 seconds**.
3. Watch the live results and CloudWatch metrics for the ALB, EC2 instances, and ASG.
4. Use **Stop** to end early; the run also stops automatically at the selected duration.

The app accepts AWS ALB DNS names ending in `.elb.amazonaws.com` or `.elb.amazonaws.com.cn`, uses GET requests, allows 1–20 requests/second and 1–60 seconds, and limits each run to 1,200 requests. Failed requests, response statuses, and average latency are included in the dashboard results. Requests are generated by the machine running this app; they are not generated by the browser.

## Run as an EC2 target

Set the app to listen on all interfaces and the port used by the target group. For example, on Amazon Linux, install Node.js, copy this project to the instance, then run:

```bash
HOST=0.0.0.0 PORT=80 npm start
```

Allow inbound traffic to the application port from the **ALB security group**. For the dashboard and unauthenticated chaos controls, limit access to trusted lab clients; do not expose them to the public internet. Set the ALB target-group health check path to `/health`. Install the app and its dependencies on every ASG instance, typically through a launch template/user data or an image.

## Main endpoints

| Method | Path | Purpose |
| --- | --- | --- |
| `GET` | `/` | Dashboard |
| `GET` | `/health` | Target-group health check (`200` healthy, `503` unhealthy) |
| `GET` | `/api/work` | Simple endpoint for generating/observing requests |
| `GET` | `/api/dashboard-data` | Live metrics, recent logs, and load-test status |
| `POST` | `/api/chaos/config` | Configure error rate, latency, and health state |
| `POST` | `/api/chaos/cpu` | Start a timed CPU spike |
| `POST` | `/api/chaos/memory` | Start a timed RAM spike |
| `POST` | `/api/chaos/load-test` | Start a bounded ALB load test |
| `POST` | `/api/chaos/load-test/stop` | Stop the active load test |

The `/api/chaos/config` request accepts optional `errorRate` (0–100), `latency` (0–30,000 ms), and `isHealthy` (boolean) fields.
